Potential Security Threats

HIGH

Authentication Attacks

Attackers may attempt to access accounts using compromised credentials.

Mitigation: MFA, strong password policies, rate limiting.
HIGH

Authorization Attacks

Users may attempt to access resources outside their permitted role.

Mitigation: Server-side authorization checks and least privilege.
HIGH

SQL Injection

Malicious input may attempt to manipulate database queries.

Mitigation: Parameterized queries and input validation.
HIGH

Cross-Site Scripting

Untrusted content may attempt to execute scripts in a browser.

Mitigation: Output encoding, sanitization, and CSP.
MEDIUM

Denial-of-Service

Excessive requests may reduce application availability.

Mitigation: Rate limiting and traffic monitoring.
HIGH

Credential Attacks

Stolen or reused credentials can be used to access accounts.

Mitigation: MFA and credential protections.
HIGH

Data Leakage

Sensitive information could be exposed through insecure handling.

Mitigation: Encryption, access control, and minimal data collection.
HIGH

Unauthorized Access

An attacker may attempt to reach protected resources.

Mitigation: Authentication, authorization, logging.

STRIDE Analysis

S — Spoofing

Pretending to be another user. Protect with strong authentication and MFA.

T — Tampering

Unauthorized data changes. Protect with validation and integrity controls.

R — Repudiation

Denying an action occurred. Protect with appropriate audit logging.

I — Information Disclosure

Exposure of confidential data. Protect with encryption and access controls.

D — Denial of Service

Making services unavailable. Protect with rate limiting and monitoring.

E — Elevation of Privilege

Gaining excessive permissions. Protect with least privilege and authorization checks.

ASSIGNMENT 3 · SECURE WEB ARCHITECTURE

Designing a Secure PhishAware Platform

How PhishAware works today, and how its architecture would evolve into a secure, account-based phishing analysis service.

CURRENT IMPLEMENTATION

Static educational website

GitHub Pages serves HTML, CSS, JavaScript, and images over HTTPS. The quiz, chatbot, and phishing analyzer run in the visitor's browser. There is no custom backend, database, login, or server-side session today.

PROPOSED ARCHITECTURE

Secure full-stack expansion

A dedicated web/API server would support user accounts, server-side phishing analysis, protected data storage, access controls, and monitored sessions. These are design decisions, not deployed features.

Architecture & data flow

Proposed design: browser → HTTPS web server → authenticated application API → database. The current site uses only the browser and GitHub Pages portions.

Proposed

Input validation

Future API validates email length and format, limits request size, escapes displayed content, and avoids executing pasted links or HTML.

Server-side controls proposed

Example: checking a suspicious email

  1. Submit: The user pastes a suspicious email into the frontend.
  2. Protect: HTTPS encrypts the request to the future API; rate limits and input validation reject unsafe or oversized requests.
  3. Analyze: The application layer runs the detection model and creates a risk explanation without opening links in the email.
  4. Control access: If saving is enabled, the server checks the user's identity and permission before writing an encrypted record.
  5. Respond: The frontend shows a risk score, warning signs, and safety guidance without rendering untrusted HTML.

Security principle: Do not store pasted email content by default. If saved analyses are added later, request consent and apply retention limits. This design also supports STRIDE mitigations for spoofing, tampering, information disclosure, and denial of service.

KAGGLE RESEARCH PROJECT

Can Machine Learning Detect Phishing Emails?

PhishAware: Comparative Evaluation of Machine Learning and Natural Language Processing for Email Threat Detection

Research design

Research problem

Phishing emails impersonate trusted senders and attempt to steal credentials or sensitive information. This study aims to determine how effectively different classifiers can distinguish phishing messages from legitimate emails.

Why this project?

It extends PhishAware's current educational, rule-based email checker toward evidence-based phishing detection and connects security awareness with measurable machine-learning research.

DATA SOURCE

Kaggle email datasets

Research input: labeled phishing and legitimate email text. The study will use labeled email text to compare traditional machine learning with transformer-based classification.

Browse Kaggle phishing datasets ↗

The study distinguishes phishing from general spam and emphasizes reliable labels.

CENTRAL RESEARCH QUESTION

How effectively can machine-learning models detect phishing emails?

Which of Logistic Regression, Random Forest, and DistilBERT offers the best balance of detection performance and computational efficiency?

RESEARCH AIM

Evaluate and improve phishing detection

Compare machine-learning approaches for distinguishing phishing emails from legitimate messages and explore how the findings could improve PhishAware.

RESEARCH HYPOTHESIS

Does context-aware language modeling help?

DistilBERT may identify sophisticated phishing language more effectively than traditional models, but only experiments can determine whether this hypothesis holds.

Why Compare Three Different Models?

01 · BASELINE

Logistic Regression

TF-IDF text features, fast to train, easier to interpret.

Question: Can a simple model already perform well?
02 · ENSEMBLE

Random Forest

Multiple decision trees can capture nonlinear feature patterns.

Question: Do richer patterns improve classification?
03 · TRANSFORMER

DistilBERT

Uses pretrained contextual language representations; requires more compute.

Question: Does context justify the extra cost?

Research Objectives

  1. Choose and validate a labeled Kaggle email dataset, carefully distinguishing phishing from ordinary spam.
  2. Clean and prepare email text and create fair training, validation, and test splits.
  3. Train and compare Logistic Regression, Random Forest, and DistilBERT.
  4. Evaluate accuracy, precision, recall, F1-score, and computational efficiency.
  5. Identify the most suitable approach and explore its potential integration into PhishAware.

Research Methodology

01

Collect & Audit

Select a Kaggle dataset, review its provenance and labels, and check missing values, duplicates, and class balance.

02

Prepare the Data

Clean text, split data into training/validation/test sets, and prevent duplicate or source-based leakage.

03

Train & Compare

Train three proposed classifiers using the same evaluation split and compare performance fairly.

04

Explain & Apply

Study false negatives, discuss limitations, and explore how findings might improve PhishAware.

Experimental design and evaluation criteria

Research methodology

Precision

Of the messages predicted as phishing, how many are actually phishing? This measures false-alarm control.

Recall

Of all phishing messages, how many are detected? High recall is important to reduce missed threats.

F1-score

The harmonic mean of precision and recall, useful for evaluating performance on imbalanced datasets.
