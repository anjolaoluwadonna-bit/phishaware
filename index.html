MEDIUM

HIGH

HIGH

Mitigation: Encryption, access control, and minimal data collection.
HIGH

Unauthorized Access

An attacker may attempt to reach protected resources.

Mitigation: Authentication, authorization, logging.

STRIDE Analysis

S — Spoofing

Pretending to be another user. Protect with strong authentication and MFA.

T — Tampering

Unauthorized data changes. Protect with validation and integrity controls.

R — Repudiation

Denying an action occurred. Protect with appropriate audit logging.

I — Information Disclosure

Exposure of confidential data. Protect with encryption and access controls.

D — Denial of Service

Making services unavailable. Protect with rate limiting and monitoring.

E — Elevation of Privilege

Gaining excessive permissions. Protect with least privilege and authorization checks.

Example: checking a suspicious email

  1. Submit: The user pastes a suspicious email into the frontend.
  2. Protect: HTTPS encrypts the request to the future API; rate limits and input validation reject unsafe or oversized requests.
  3. Analyze: The application layer runs the detection model and creates a risk explanation without opening links in the email.
  4. Control access: If saving is enabled, the server checks the user's identity and permission before writing an encrypted record.
  5. Respond: The frontend shows a risk score, warning signs, and safety guidance without rendering untrusted HTML.

Security principle: Do not store pasted email content by default. If saved analyses are added later, request consent and apply retention limits. This design also supports STRIDE mitigations for spoofing, tampering, information disclosure, and denial of service.

ASSIGNMENT 06 · COMPUTER SECURITY

Cross-Site Scripting (XSS) Security

Learn how untrusted input could change a web page and how PhishAware safely handles text submitted by visitors.

01 · SECURITY PROBLEM

Untrusted content can become executable code

If an application inserts user-supplied text into HTML without protection, the browser may interpret it as markup or JavaScript. This can lead to unwanted page changes, data exposure, or actions performed in a user's session.

Example: A malicious comment, profile field, or chatbot message displayed as HTML rather than plain text.

02 · SECURITY CONTROL

Validate input and encode output

Check input length and type, reject invalid data, and display user content using textContent instead of interpreting it with innerHTML. Use context-appropriate output encoding and sanitization when rich HTML is truly necessary.

03 · MITIGATION

Handle visitor messages safely

PhishAware's new practice area treats typed content as text. Production applications should also enforce validation on the server, sanitize permitted HTML, use a carefully configured Content Security Policy, and protect session cookies.

04 · SECURITY IMPROVEMENT

Lower the risk of script injection

Visitors can enter questions and profile information without those messages being interpreted as executable HTML in the protected display. This reduces a common XSS risk, but does not prove the whole website is free from vulnerabilities.

Phishing emails impersonate trusted senders and attempt to steal credentials or sensitive information. This study aims to determine how effectively different classifiers can distinguish phishing messages from legitimate emails.

Why this project?

Experimental design and evaluation criteria

Research methodology

Precision

Of the messages predicted as phishing, how many are actually phishing? This measures false-alarm control.

Recall

Of all phishing messages, how many are detected? High recall is important to reduce missed threats.

F1-score

The harmonic mean of precision and recall, useful for evaluating performance on imbalanced datasets.

ASSIGNMENT 7 · CYBERSECURITY RESEARCH & FILM

Protecting Website Availability

Investigating DoS and DDoS traffic using public intrusion-detection data, and telling the story through a short cybersecurity film.

Research question

Can data-driven methods help identify abnormal network traffic associated with DoS and DDoS attacks before website availability is seriously affected?

Objective: Compare benign and malicious traffic, identify predictive flow characteristics, and evaluate defensive detection approaches.

DoS vs. DDoS

DoS: An attempt to exhaust a service's resources or capacity from one primary source.

DDoS: A coordinated disruption using many distributed sources, which can be harder to filter using simple source-based controls.

Both threaten availability, one of the three core cybersecurity principles.

Public research dataset: CIC-IDS2017

Selected source: CIC-IDS2017 on Kaggle, originally developed by the Canadian Institute for Cybersecurity. It contains labeled network-flow records, including benign activity, DDoS, and several DoS variants.

Labels: BENIGN, DDoS, DoS Hulk, DoS GoldenEye, DoS slowloris, and DoS Slowhttptest, among other attack categories. Candidate features: Flow Duration, Total Fwd Packets, Total Backward Packets, Flow Bytes/s, Flow Packets/s, packet lengths, and inter-arrival times (feature availability depends on dataset file).

Research scope: Only BENIGN, DDoS, and DoS-labeled records are considered for the binary comparison. Other attacks are excluded rather than incorrectly treated as normal traffic.

Normal network traffic

Ordinary traffic often follows a mix of user-driven requests, response packets, varying session durations, and changing packet sizes. Its volume varies with legitimate activity, so high traffic alone is not proof of an attack.

Attack-associated behavior

Possible indicators include sustained spikes in flows or packets, unusually short gaps between requests, many similar connections, high forward-to-backward packet imbalance, and bursts from multiple sources. No single feature proves an attack.

The chart below is illustrative, not measured from CIC-IDS2017. It demonstrates a potential change in traffic volume; it must not be presented as an experimental result.

Preprocessing and detection methodology

  1. Load the downloaded CIC-IDS2017 CSV files and standardize column names.
  2. Retain BENIGN, DDoS, and DoS categories; remove duplicate records and replace infinite values with missing values.
  3. Convert numerical features, inspect missing values, and summarize distributions by traffic class.
  4. Compare flow rate, packet rate, packet counts, and duration with charts and class-specific statistics.
  5. Use a stratified train/test split and a median-imputation + random-forest classification pipeline, with a fixed random seed.
  6. Report precision, recall, F1-score, and confusion matrix, including false negatives and false positives.

Download reproducible Python analysis script · Analysis instructions

Interpretation and availability

Precision describes how often an alert really corresponds to attack traffic. Recall measures how many actual attacks were caught. F1 balances the two. The confusion matrix reveals missed attacks and false alarms.

Detection can support alerting, rate limiting, traffic filtering, and capacity planning, but detection alone does not guarantee uninterrupted service.

Results, limitations, and next steps

Status: Dataset and reproducible analysis method selected. No measured model scores are claimed yet; run the included script on downloaded CSV files to generate results and replace this note.

Limitations: dataset age, possible class imbalance, lab-generated traffic, concept drift, and differences between flow classification and live website monitoring.

Next: evaluate unseen time periods, examine false negatives, and compare a baseline threshold detector with the trained model.

Research conclusion

Network-flow features provide a reasonable basis for investigating abnormal behavior linked to DoS and DDoS attacks. A defensible conclusion about how well a detector works requires evaluation on real labeled records. Combining traffic monitoring, careful classification, and layered protections can help security teams respond to threats against website availability.

Hosts file

I inspected /private/etc/hosts using sudo nano. Existing mappings were 127.0.0.1 localhost, 255.255.255.255 broadcasthost and ::1 localhost. Comments beginning with # document configuration and are ignored by the resolver. I backed up the file and temporarily added 192.168.1.1 winserv and 192.168.1.221 me. Both names resolved correctly. The gateway response took longer because it traversed the local network. I removed the two entries after testing.

A normal user cannot directly edit a properly protected hosts file. Incorrect permissions or a vulnerable privileged application could allow unauthorized changes that redirect users to malicious websites. Least privilege and file-integrity monitoring reduce this risk.

DNS cache

I ran sudo killall -INFO mDNSResponder and inspected unified logs with log show --last 5m --predicate 'process == "mDNSResponder"' --info. Logs showed completed DNS queries, resolver activity and no logged errors or faults in the inspected interval.
